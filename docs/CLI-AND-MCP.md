# CLI, MCP and API

Everything the console does goes through the REST API (`/v1`, OpenAPI 3.1 at `/openapi.json`, docs at `/docs`). The same API serves a command-line client and an MCP server, so people can work with their bots from a terminal or from any MCP client.

## Tokens

| Token | Use |
| --- | --- |
| Admin token | Generated by the Helm chart (`<release>-platform` secret, key `admin-token`). Owner of the default team. Use it to get started, or as a break-glass account. |
| API tokens (`orr_…`) | Made in the console (Settings → API tokens), with `orrery tokens create`, or with `POST /v1/tokens`. Each has a role (viewer, member, admin, owner) no higher than its creator's. Admins can make a token for a named person (`--for Alice`). Only a SHA-256 is stored; revoking takes effect within 30 seconds. |
| OIDC access tokens | When an identity provider is configured, the console signs in with it. |

## CLI

The install serves the CLI, so its version always matches the server:

```sh
curl -fsSLo orrery https://orrery.example.com/cli/orrery.mjs && chmod +x orrery   # Node.js 20+
./orrery login --url https://orrery.example.com --token <token>
```

```text
orrery whoami | status                 who you are; what the install has configured
orrery bots                            list bots
orrery bots create Ada --engine kiro|kiro-v2|opencode|openai [--model …]
orrery ask Ada "why is staging slow?"  one turn: the answer streams, then the command exits
orrery chat Ada                        interactive; approvals are asked inline
orrery groups create ops Ada Scout     a group (the first bot leads)
orrery ask ops "@Scout check the dashboards"
orrery approvals | approve <id> [--always] | deny <id>
orrery tokens [create <name> | revoke <id>]
orrery env [set NAME [value] | rm NAME]   agent credentials (KIRO_API_KEY, ANTHROPIC_API_KEY, …)
orrery mcp [--client claude|cursor|vscode]
```

Notes:
- `ORRERY_URL` and `ORRERY_TOKEN` override the saved login.
- `--json` prints machine-readable output.
- `--approve` lets non-interactive runs (CI, scripts) approve tool calls once, automatically.
- In `chat`, `/steer <text>` guides the running turn, and Ctrl+C stops it.

## MCP

`/mcp` (Streamable HTTP) gives a different tool set depending on the token:

- **A person's token** (API token, admin token or OIDC) gets tools to work *with* the bots:
  - `list_bots`, `list_groups`;
  - `ask_bot`, which sends a message to a bot or group and waits for the reply;
  - `wait_for_reply`, `get_conversation`, `list_conversations`;
  - `list_approvals`, `decide_approval`.

  Roles apply: viewers can read, members can ask and decide, and standing permission (`allow_always`) needs an admin.
- **A bot-scoped platform token**, which Orrery gives each agent session, gets the agent's own tools: memory, knowledge, conversation history and delegation.

`orrery mcp` prints the client configuration:

```json
{ "mcpServers": { "orrery": { "type": "http", "url": "https://orrery.example.com/mcp", "headers": { "Authorization": "Bearer orr_…" } } } }
```

If a tool call needs approval, `ask_bot` returns `status: "waiting_approval"` together with the pending approvals. The client decides each one with `decide_approval` and then calls `wait_for_reply`.

## Groups

A group is one conversation with 1–6 bots and any number of people, like a group chat:
- A message goes to the bots it **@mentions** (`@all` reaches every bot). With no mention, it goes to the **lead**, which is the first bot.
- A bot hands work to another by mentioning it in its reply. The other bot answers in the same conversation. A chain of hand-offs stops after six.
- Each bot keeps its own agent session for the group. At each turn it is told who is in the group and what was said since it last spoke.

API:
- `POST /v1/groups {name, botIds}`
- `POST /v1/groups/:id/messages {text}`
- The group's thread works with the usual `/v1/threads/:id/…` endpoints: messages, runs and the event stream.
